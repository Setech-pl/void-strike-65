# Music sources

Engineering document, English only (`docs/README.md` §"Documentation
language").

`menu-theme.json` is the editable source for the menu theme **"sketch B"**,
in **format 2**. `gameplay-theme.json` is still the format-1 gameplay theme
"Contact Line"; plan `docs/plan-music-v2.md` §10 step 2b replaces it with the
format-2 "GRA-2" draft in `v2-drafts/`.

Generated bytes under `build/` are never edited by hand. The JSON is the
source; the per-frame POKEY register stream it implies, as the reference
renderer interprets it, is the specification.

---

## Auditioning a change

```
python3 assets/music/preview/render.py assets/music/menu-theme.json /tmp/menu.wav
```

`preview/render.py` is the reference renderer. It reads a theme and writes a
WAV; it never writes a JSON. `--loops N` plays the loop N times (default 2),
and `--pitches FILE` takes the pitch table from another theme, which is how
the gameplay theme borrows the menu's.

Edit the JSON, render, listen, then build. It needs `numpy` and `scipy`, like
every preview tool here; nothing in `npm run build` depends on it.

`preview/sketches/` holds the generators that composed the approved v2 drafts.
They are provenance and refuse to run without `--write`; they write into their
own directory, never over `assets/music`.

The register-stream tests pin the approved music by SHA-256 of the source and
of the stream it implies, so a deliberate retune fails the build until the
owner has accepted the new sound and the pins are re-recorded in the same
commit.

## The format-2 schema

| Key | Meaning |
| --- | --- |
| `formatVersion` | `2` |
| `targetFrameHz` | `50`; PAL only |
| `audctl` | `0`. Channels 3 and 4 are SFX-owned and share POKEY's clock; the converter refuses anything else |
| `framesPerRow`, `rowsPerPattern` | the transport. Menu: 6 frames a row, 16 rows a bar |
| `channels[]` | one entry per POKEY channel, with its `role`, and `preemptedBy` where SFX take it |
| `pitches[]` | `{ id, kind, divider }`. `kind` is `pure` (AUDC `$Ax`), `buzz` (`$Cx`) or `noise` (`$8x`). The **pure block comes first and is chromatic and contiguous**, so an arpeggio offset of *k* semitones is simply "table index + *k*" |
| `instruments{}` | `{ distortion, volume[], arp[] }`. `volume` is a per-frame envelope whose **last entry is held**; `arp` is a per-frame list of table-index offsets that **cycles** |
| `drums{}` | per-frame macros of `[distortion, divider, volume]`, played once and then silent |
| `patterns{}` | named bars of `rowsPerPattern` rows; each row has one token per channel |
| `sequence[]` | the bar order |

Tokens are `"HOLD"` (keep playing, keep advancing), `"REST"` (silence and
forget the voice), `"INSTRUMENT:PITCH"`, or a bare drum name.

### The renderer's rules

These are what the music *is*, and three independent things implement them:
`preview/render.py`, `scripts/music-oracle.mjs`, and the 6502 player.

* A new token resets the envelope and the arpeggio to their first entry.
* `HOLD` keeps advancing them; the envelope holds its last entry for ever,
  the arpeggio wraps to its first.
* `REST` publishes AUDC `$00` and forgets the voice.
* A volume of 0 publishes AUDC **`$00`**, not `distortion | 0`. Same silence,
  different byte — and the stream is the specification.
* AUDF is **not written** while a channel is silent; its divider is
  don't-care there.
* A drum plays one `(AUDC, AUDF)` pair a frame and is silent once its macro
  runs out.

## The compiled encoding

`scripts/music.mjs` compiles the JSON into `build/menu-music.inc`:

| Block | Size (menu) | Notes |
| --- | ---: | --- |
| `music_pitches` | 43 B | dividers only; distortion is an instrument property |
| `music_macro_page` | 51 B | envelopes, arpeggios and drum macros, each stored once. **One page max**: a cursor into it is one byte. Bit 7 marks an envelope's last entry ("hold here") and an arpeggio's last entry ("wrap to start"); a drum macro ends at a `$00` byte |
| `music_instrument_{audc,macro,arp}` | 3 × 8 B | one record per instrument, in channel order |
| `music_channel_base` | 4 B | where each channel's instruments start |
| `music_sequence` | 32 B | one column id per channel per bar |
| `music_column_{lo,hi}` | 2 × 20 B | column addresses |
| `music_column_*` | 20 × 16 B | the 16-row columns themselves, deduplicated (5 / 2 / 8 / 5 distinct per channel) |
| **total** | **514 B** | |

A row token is one byte: `$00` HOLD, `$01` REST, otherwise
`select(2 bits) << 6 | (pitch index + 2)`. `select` picks one of up to **four**
instruments from the channel's base, which is how eight instruments and 43
pitches fit in one byte. The `+ 2` bias is why a drum token with `select = 0`
is not `$00` and cannot be mistaken for HOLD.

## Validation the converter enforces

* **The buzz rule.** Distortion `$C` runs the 4-bit polynomial, period 15
  clocks, so a divider whose `(N+1)` is divisible by 3 or 5 aliases into a
  lower-order pattern and stops sounding like a pitch. Every `$C` divider, in
  `pitches` and in every drum macro, must pass. This is what stops a retune
  turning the bass line into noise silently.
* The pure block is first, chromatic and contiguous.
* At most **four** instruments per channel (two select bits).
* A volume of 0 may only be an envelope's **last** entry, so silence is
  terminal — the player stops advancing a held envelope and skips the
  arpeggio step while a voice is silent.
* A drum frame's volume is 1-15, so `$00` can terminate the macro.
* The macro page fits 255 B.
* An arpeggiated note plus its widest offset stays inside the pure block.
* `audctl` is 0; all four channels are documented.

## Placement and cost

| | where | size |
| --- | --- | ---: |
| Menu player | `STARFIELD`, in main's link | 353 B code |
| Menu score | `STARFIELD` | 514 B |
| Menu state | 4 transport counters at `$4ED9`; 20 B of voice state in the PairShot RAM tail at `$548A`; 10 B of zero page at `$A2` | 34 B |
| Gameplay player + score (v1) | the **per-level image**, executing from `$A608` behind three frozen vectors (music v2 §1.4, owner answer Q-P1) | 222 + 138 B |

The menu tick costs 383-492 cycles on an ordinary frame, 515-920 on a row
frame (the peak is a bar-load frame). There is no fence in the frontend: it
runs right after `wait_frame`, about ten scanlines of CPU before the input
poll and far above the footer DLI. Stated, not gated.

## The mix, and SFX

The v1 rule "summed POKEY volume ≤ 13" belonged to the v1 cinematic mix and
is **gone**. Sketch B peaks at a summed volume of **41** (kick 13 + bass 11 +
lead 11 + arpeggio 6) on 410 of its 768 frames. Owner decision AB, Q-V1:
**nothing is rescaled**; the owner judges it in the emulator, and if it clips
the answer is per-instrument volume edits in the JSON, re-auditioned through
the renderer — not a player change. The converter reports the peak into
`build/manifest.json` as `menuMusic.peakVolumeSum`.

The menu owns all four voices; nothing preempts it. In gameplay channels 1
and 2 carry the music and channels 3 and 4 are SFX-only (engine bed,
capital-hull explosion). Owner answer Q-S1 moves the Player Fighter shot SFX
to channel 4 so the bass on channel 1 is never preempted and the lead on
channel 2 stops only for hits — that lands with the v2 gameplay player in
plan §10 step 2b, and `gameplay-theme.json` still documents the v1 policy
until it does.
