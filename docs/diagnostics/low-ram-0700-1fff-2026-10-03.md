# `$0700-$1FFF` is never written at runtime (2026-10-03, M5a-S2)

**EMULATOR-MEASURED.** Atari800 7.1.2 PAL/XL, a scratch copy of the
instrumented `build/atari800-trace` (the copy and its probe were not
committed; nothing in the harness changed). Recorded because owner decision
2026-10-03 rests on it: the level-summary module lives at `$0500-$0BFF`
(`cfg/level-summary.cfg`), and `$0C00-$1FFF` is recorded as an unclaimed lever.

## Why the question came up

The plan (`docs/plans/m5-loading-boss.md` §4.8.1) priced the summary module at
400 → 480 B for the splash RAM `$0500-$06FF` (512 B). Its first build MEASURED
**1,359 B**, and the save-record write path (~110 B) had to leave the sector
reader, which overflowed its 1,536 B by 96 B. While looking for room, no link
config, segment, equate or document claimed `$0700-$1FFF`.

## Static evidence

* No `MEMORY` area in `cfg/*.cfg` and no linked segment in any `build/*.map`
  lies in `$0700-$1FFF` (below `$2000` only zero page, the stack, the OS page
  2-3 vectors and the boot splash at `$0500-$06FF`).
* No equate in `src/` names an address in `$0400-$1FFF` (grep).
* The boot loads the initial block at `$2000`; stage 2's SIO buffer
  (`DBUFLO/HI`) is `CHUNK_STAGING_ADDRESS` (`$8100` staging); `MEMLO` is set to
  `$3B00`.
* The game takes the machine over (`sei`, no OS VBI, no CIO, no SIOV after
  stage 2), so no OS routine runs that would use the area.

## Measurement

Main `f349c80`, ATR `84c7af52…`. The probe wrote a pattern over all of
`$0700-$1FFF` at the first instruction of `start` (`$201E`, the game's
takeover; frame 233 without BASIC, 224 with it), then drove the production
frontend: FIRE at the menu from frame 3,050 and a 6-frame FIRE pulse every 400
frames, which plays START GAME → gameplay (the fighter idles and dies) →
GAME OVER → the menu → START GAME again. Every 1,000 frames from 3,000 to
20,000 it counted the bytes of `$0700-$1FFF` that differed from the pattern.

| BASIC at coldstart | pattern | game states seen (menu 1, gameplay 6, GAME OVER 7) | bytes changed, frames 3,000-20,000 |
| --- | --- | --- | ---: |
| off (`-nobasic`) | `$5A` | 1, 6, 7, three games | **0 of 6,400** |
| on (`-basic`) | `$5A` | 1, 6, 7, three games | **0 of 6,400** |
| off (`-nobasic`) | `$A5` | 1, 6, 7, three games | **0 of 6,400** |
| on (`-basic`) | `$A5` | 1, 6, 7, three games | **0 of 6,400** |

The emulator's own cold RAM content was left as Atari800 sets it (the harness's
`DFTRACE_RAM_FILL`/`DFBOOT_RAM_FILL` only touch `$8000-$9FFF`); the pattern
written at `start` is what makes a later write visible, whatever the cold fill.
The pause screen, the OPTIONS screen and TOP SCORES were not visited; their code
is in the same links the static evidence covers.

## What it does and does not prove

It proves the game, as shipped on `main`, neither links nor writes anything in
`$0700-$1FFF` after `start` on the emulator. It does not prove real hardware
behaves the same — Atari800 cannot vouch for that (debt items 2 and 5). The
owner's smoke covers it: the summary screen working after several games and a
GAME OVER on the 65XE shows the range holds on the machine
(`docs/hardware-testing.md`, M5a-S2 items).

## Probe recipe (for the next session that needs it)

Copy `build/atari800-trace` elsewhere, add a function at the top of
`DFTrace_Observe` that fills the range at `pc == start` and counts differences
per frame, `make`, and run it with `SDL_VIDEODRIVER=dummy` on a copy of the ATR
**given by a short relative path**: from the session scratchpad's long absolute
path the image failed to mount and the OS fell into the self-test at `$505E`.
