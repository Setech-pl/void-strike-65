## 5. Question 1d — the four placement options

All four are costed against: **~400 B of Director code/data**, the free space
of §2 and §3, the binding fence margin **2,981 cycles**
(`director-complete-1-natural-sweep-fire0` frame 3631, MEASURED native at
`9fc73b9`), transport **205 sectors / 515 free ATR sectors**, and the ATR boot
milestones **339 loader / 596 menu** against a +10 warn, +50 fail band.

**One fact retires two of the four options before their costs are read.** A
`jsr` to an absolute address in the window costs exactly what a `jsr` anywhere
else costs. There is no banking, no copy, no trampoline: `disable_basic_rom`
forces PORTB bit 1 at every stage-2 entry, so `$A000-$BFFF` is unconditionally
RAM for the whole runtime, and `main.s` already reaches both the reader
(`$A000`) and the Light kernel (`$B921`) by constant. **Cross-window call cost
is 0 cycles for every option below.**

### (a) Director resident in the window, loaded once at boot

**How.** Shrink `LEVEL_BUFFER` from 32 to 16 sectors and give the freed 2,048 B
to the code window: reader `$A000-$A5FF`, buffer `$A600-$ADFF` (2,048 B, 283 B
of headroom over the 1,765-B worst-case payload), code window
`$AE00-$BBFF` = 3,584 B, of which 1,509 are the Light kernel → **2,075 B free**.

**Edit surface, MEASURED (four places, all guarded):** `levelBufferSectors`
in `scripts/build.mjs:145`; the two MEMORY blocks in `cfg/sector-reader.cfg`
and `cfg/encounter-director.cfg`; `LEVEL_BUFFER` stays at `$A600`
(`src/hybrid/sector-reader.s:127`) and only the window base moves.
`scripts/build.mjs:1891` already refuses a window that starts inside the
buffer, and `src/hybrid/light-kernel.s` already asserts its own base against
`HYBRID_ASM_WINDOW_BASE`. Owner decision X performed this exact move at 44 → 32.

### (c) Split — hot per-frame path below `$A000`, cold per-wave code in the window

**The project has measured this principle and found it inverted.** MEASURED at

once per admission** — and the *hot* multi-slot kernel stayed. The commit's own
reasoning is recorded: "an absolute `jsr` costs the same either way". Heat does
not select a segment on this machine; **room does**.

## 6. Recommendation — option (a), with (c)'s one useful detail

**Shrink `LEVEL_BUFFER` from 32 to 16 sectors and place the 4.6 Director in the
window at `$AE00`.** Keep the small per-frame deltas (path state in the Light
tick, the wave stepper's call) in the arena's 114 B where they already fit, and
keep the 6 B of Director state in the unowned `$8128-$813F`.

Why this and not the others, in one line each: (b) reopens owner decision C and
converts a data-integrity failure into a code-integrity failure for 400 B that
(a) gives away; (c) fills every remaining fragment to its last byte and
guarantees the placement churn Light multiplicity paid for three times; (d)
spends a boot-order refactor on a problem a config change solves.

**What the owner is actually being asked to accept:** 2,304 B of level buffer
sized for a payload nobody has designed, traded for 2,048 B of code space, with
283 B of buffer headroom left over one full art set plus both LevelDef pages.
If a later level needs more than 16 sectors, the trade reverses with the same
edit and the build says so before the binary exists.

**Preconditions, all satisfied at HEAD:** the reader is implemented and the
image at `$A600` is verified byte-exact on every boot-smoke session; the window
is unconditionally RAM; `scripts/build.mjs` already refuses a window that
overlaps the buffer; decision X is the precedent.

**Not in this recommendation:** any change to the reader protocol, the level
directory, `levelBaseSector`, or the number of levels the ATR holds. Only the
buffer's *size* moves.

## 7. Question 2 — the Bomber breakup

### 7.1 Today's Heavy death path, MEASURED from source

Trace, in call order:

1. `update_enemy_damage` (`main.s:5150`) → `HYBRID_ENEMY_APPLY_PENDING_DAMAGE`
   → `enemy_c_apply_pending_damage` (`lifecycle.c:959`). **Per member.** On
   lethal it clears that member's state, decrements `ENEMY_LIVE_COUNT`, and
   when the count reaches 0 sets `ENEMY_ACTIVE = ENEMY_EXPLODING_STATE`.
2. `erase_enemy_member` — **the P1/P2 body is erased on the kill frame.**
3. `spawn_interceptor_breakup_effects` (`main.s:10300`), whose entire body is
   `jmp begin_enemy_fighter_explosion`, above a comment that states the design
   explicitly: *"Raider destruction is PMG/background feedback only. Do not
   touch the shared character-effect pool."*
4. `begin_enemy_fighter_explosion_tail` (`main.s:11489`, 62 B in `ENTITY_CODE`)
   computes the member's screen X and Y, stores them in
   `FIGHTER_EXPLOSION_X/Y + FIGHTER_EXPLOSION_ENEMY_SLOT`, and loads
   `FIGHTER_EXPLOSION_TIMER + ENEMY_SLOT` with
   `SHARED_FIGHTER_EXPLOSION_TOTAL` = 24.
5. Score, sound, `HITCLR`, pickup-kill accounting — all on the kill frame.

**What renders after that: nothing.** MEASURED, and this is the finding:

* `render_shared_fighter_explosions` (`main.s:4561`) reads
  `FIGHTER_EXPLOSION_TIMER + FIGHTER_EXPLOSION_PLAYER_FIGHTER_SLOT` only.
  **The six-phase PMG explosion is never drawn for the enemy slot.** The
  masks exist (`shared_fighter_explosion_masks`, 6 phases × 4 frames = 24) and
  are used by the player death alone.
* `FIGHTER_EXPLOSION_X/Y + ENEMY_SLOT` has exactly **one reader** in the whole
  source: `weapon_pickup_record_qualified_kill` (`main.s:9851`), which uses the
  X to place a pickup capsule. No renderer touches it.
* The only visible enemy-death feedback is a **COLBK flash for
  `ENEMY_FIGHTER_FLASH_FRAMES` = 4 frames** (`main.s:6877`), from
  `enemy_fighter_flash_colors`.

So the 24-frame timer is a **lifecycle hold before recycle**, not an animation,
and the player sees: the ship disappears, the background flashes for 80 ms.
**"Vanishes in a flash" is the literal implementation, not a regression** —
which matches the earlier check.

**Scale, MEASURED** (`build/enemy-roster.inc`): the Bomber
(`ENEMY_ARCHETYPE_SCYTHE_BOMBER` = 2) is frame height **16 scanlines**, size
mode **3 = quad width**, visible width **32 HPOS** — eight character cells wide
by two rows, sixteen cells of silhouette. The shared explosion is 8 HPOS × 8
scanlines. Even if it *were* drawn for the enemy slot it would cover one
sixteenth of the hull. The Raider, for comparison, is 14 scanlines and 16 HPOS
(double width).

**A Bomber is two members.** `enemy_c_apply_pending_damage` runs per member, so
one Bomber formation produces up to **two** death events, and there is exactly
one `FIGHTER_EXPLOSION_ENEMY_SLOT`: the second overwrites the first.

### 7.2 The machinery available for reuse

| Piece | What it is | MEASURED |
| --- | --- | --- |
| `spawn_breakup_effects_at` (`main.s:10252`) | A = X, Y = Y → 1 core + 4 fragments in the shared effect pool | core glyph = `ENTITY_RENDER_ID`, fragments = `EFFECT_FRAGMENT_GLYPH_BASE` = 118; all four at +4/+4 from the anchor |
| `light_spawn_breakup` (`light-kernel.s:501`) | **the template**, 12 B: `jsr clear_transient_effects` / `jsr light_top` / `tay` / `ldx LIGHT_SLOT` / `lda LIGHT_X,x` / `jmp spawn_breakup_effects_at` | 12 B |
| The effect pool | `EFFECT_SLOT_COUNT` 6, `EFFECT_ACTIVE_LIMIT` **5** — one core + four fragments, **one instance at a time**; `clear_transient_effects` wipes the previous one | `build/entity-effects.inc` |
| Lifetimes | core 5 frames, fragments **30 frames** | `EFFECT_DEBRIS_CORE_FRAMES` 5, `EFFECT_DEBRIS_FRAGMENT_FRAMES` 30 |
| Debris glyphs 110-117 | `ENTITY_DEBRIS_GLYPH_BASE` = 110, 8 glyphs, 2 variants × 2 phases × 2 cells | the *interactive entity* bank, used by live debris — the breakup core borrows one via `ENTITY_RENDER_ID`; fragments use 118-119 |
| The 6-phase explosion | `shared_fighter_explosion_masks`, 6 phases × 4 frames, 8×8, renders to **P0 and P3** | P0 is the player fighter and P3 is the pickup mark — **it cannot be reused for an enemy while the player is alive** |
| The token | `light_take_deferrable_token()` in the window, 13 B; the rotate gate; `BREAKUP_PENDING` as the deferred-once bit | MEASURED, shipped at `9fc73b9` |

**Two constraints fall straight out of that table and shape every variant:**

1. **The effect pool holds one breakup.** A two-member Bomber cannot produce
   two simultaneous clusters without growing `EFFECT_SLOT_COUNT` from 6 to 11
   — 5 × 18 SoA arrays = **90 B of BSS**, and `ENTITY_STATE` is 256 B with
   `liveFieldBytes` 212, i.e. 44 B spare. **It does not fit.** Two clusters is
   therefore not a cheap variant; it is a pool redesign.
2. **The 6-phase explosion renders to P0/P3.** The Heavy's own **P1/P2 are free
   the instant `erase_enemy_member` runs**, so a Heavy explosion belongs there
   — which is a new renderer, not a reuse.

### 7.3 The token contract a Bomber breakup must satisfy

Per owner decision 2026-09-21 (effect scheduling) every new consumer must be
visual only, capture its position at enqueue, and be forced or dropped within
two frames. A Bomber breakup satisfies all three, and the position is *already*
captured: `begin_enemy_fighter_explosion_tail` writes
`FIGHTER_EXPLOSION_X/Y + ENEMY_SLOT` on the kill frame, before anything can
move. That is the enqueue, and it costs 0 new bytes.

* **DEFERRABLE consumer**, claiming through `light_take_deferrable_token()` —
  the same wrapper, so the rotate gate applies with no new code.
* **Deferred-once forcing rule.** The Light uses `BREAKUP_PENDING` as its one
  bit of history. The Heavy has no equivalent, so it needs **1 B** of pending
  state. `HYBRID_HEAVY_STATE` is 11 B and exactly full; the byte goes to the
  unowned `$8128-$813F` (24 B) as its own segment with named ld65 asserts —
  the answer fix (a) and the rotate gate both gave, twice.
* **The retry site.** `update_enemy` (`main.s:4608`) already runs every frame
  while `ENEMY_ACTIVE == ENEMY_EXPLODING_STATE` and returns early on the
  explosion timer. The ungated second attempt goes there: ~10 B.
* **Kill, score and sound stay on the kill frame**, unchanged — they already do
  (`main.s:5168-5180`), and nothing in any variant gates them.
* **Delay bound: 2 frames.** Rotate frames are never consecutive (proved
  against the source in `main.s`, re-run over the rate table for all three
  difficulties), and the second attempt is ungated.

**One player-visible consequence to put to the owner.** The member's body is
erased on the kill frame by `erase_enemy_member`, and the fragments arrive 1-2
frames later. For 20-40 ms the Bomber is gone and nothing has replaced it. The
Light has exactly this gap today and it was accepted; the Bomber is eight cells
wide, so the same gap is eight times more visible. The 4-frame COLBK flash
covers it — which is an argument for **keeping** the flash rather than
replacing it.

### 7.6 Interaction with the admission rule and with contact damage

**Heavy and swarm never coexist** (plan §2.4, two C-decided guards: the wave
lock denies `_asm_director_can_allocate`, and a wave never starts while
`ENEMY_ACTIVE != 0`). In a Heavy sector the ceiling is
`LIGHT_CEILING_ELITE = 1` — the escort. Consequences, all favourable:

* On a Bomber death frame there is **at most one Light alive**, so the token
  has at most one other deferrable claimant. The worst case is one Bomber
  member's breakup and one Light breakup on the same frame: the token
  serialises them to consecutive frames, which is exactly what it is for.
* **The two Bomber members are the real contention.** Both can die on one
  frame. The token serialises them anyway, and the single effect pool means the
  second `clear_transient_effects` wipes the first cluster after 1-2 frames.
  **Player-visible: the first member's fragments are cut short.** Options: let
  the second member's claim be refused while a breakup is live (one compare,
  ~6 B — the first member's cluster stands for the whole death); or accept the
  truncation. **Owner question Q-3.**
* **The binding rows are unaffected.** `director-complete-1-natural-sweep-fire0`
  f3631 (2,981) is a Light-swarm row with no Heavy; by the admission rule a
  Bomber breakup cannot occur there. The Heavy rows are at 3,972 / 4,179.

**Debris contact damage — the fragments do not hurt the player, and that is
already true of the Light.** MEASURED: contact damage lives in
`entity_collide_player` (`main.s:10183`), which runs over the **interactive
entity pool** (`ENTITY_*`, `ENTITY_ACTIVE_LIMIT` 2 — live debris and the pickup
slot). `spawn_breakup_effects_at` fills the **effect pool** (`EFFECT_*`), whose
own comment calls it "the generic collisionless renderer"; no collision path
reads `EFFECT_*`. So Light breakup fragments are decorative today, and Bomber
fragments through the same pool would be too.

**Propose, do not decide (owner question Q-2).** The case for leaving them
harmless: it is the existing contract, it costs 0 bytes, and a 32-HPOS-wide
spray of damaging cells appearing where the player just scored a kill is a
punishing, unreadable hazard. The case for making them hurt: a capital ship
breaking up *should* be dangerous, and the machinery exists (the interactive
pool already does contact damage with a difficulty-scaled table). The cost if
the owner wants it is not the collision test — it is that the fragments would
have to move to the **interactive** pool, whose active limit is 2. **That is a
pool redesign, the same wall variant "two clusters" hits.** Recommend: leave
them harmless, and revisit if 4.8a's bigger debris changes the pool anyway.
