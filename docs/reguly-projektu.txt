VOID STRIKE 65 — reguły projektu

Wersja 3.2 — 2026-09-20
Generacja: hybryda C/cc65 + ca65 (Hybrid C Director owner-accepted), po Light Wingman M1.
Zastępuje wersję 2.1 („po Stage 2B.2”), zachowaną w docs/history/reguly-projektu-v2.1.txt.
Historyczne reguły nie mają pierwszeństwa przed tym plikiem.

Zmiana 3.1 → 3.2: reguła 11 oznaczona SUPERSEDED (decyzje właściciela A, B, C, Q).
Treść reguły zostaje jako historia; obowiązuje to, co w niej wskazano jako nadal w mocy.

1. Cel

Celem jest ukończenie grywalnej gry na Atari 65XE PAL 64 KB w rozsądnym czasie. Architektura ma służyć grze; nie przedłużamy projektu, aby zachować elegancki model techniczny.

2. Źródła prawdy i handoff

Repozytorium jest źródłem prawdy, nie historia rozmów ani pamięć agenta. Kolejność pierwszeństwa opisuje docs/README.md:
1. bieżący lokalny Git, kod i wyniki buildu;
2. docs/STATUS.md;
3. ten plik;
4. docs/plan-realizacji.md;
5. dokumenty domenowe (game-design, architecture, hybrid-c-architecture, memory-map);
6. decyzje właściciela;
7. diagnostyki;
8. historia.

Nowsze zaakceptowane decyzje mają pierwszeństwo przed starszymi diagnostykami i historią. Wygenerowane pomiary buildu/mapy mają pierwszeństwo przed ręcznie przepisanymi liczbami.

docs/STATUS.md jest podstawowym handoffem pomiędzy Claude Code, Codex, agentami lokalnymi i właścicielem.

Na granicy nowej sesji lub nowego zadania obowiązkowe są wyłącznie: stan Gita (branch, HEAD, git status) oraz docs/STATUS.md. Pozostałe dokumenty dobiera się do typu zadania zgodnie z AGENTS.md i mapą w docs/README.md — nie każde zadanie musi przeładowywać reguły, plan i architekturę. Niezmienionej dokumentacji nie wczytuje się wielokrotnie w obrębie jednej sesji.

Każde zaakceptowane zadanie kończy się aktualizacją STATUS.

3. Git

- Nie resetuj, nie usuwaj, nie nadpisuj i nie stage'uj cudzych zmian; brudne drzewo może być celowe.
- Jedno zadanie = jeden główny wynik; osobne, skupione commity lokalne są dozwolone.
- Push, merge, tag i release wyłącznie po decyzji właściciela.
- Git jest podstawowym mechanizmem rollbacku; przed eksperymentem zabezpiecz punkt odniesienia.
- Nie dotykaj .claude/.

4. Hybryda C/cc65 + ca65

Zasada: jeżeli nowe zachowanie gameplayowe da się wyrazić jako decyzja albo przejście stanu, domyślnie należy do C. ASM konsumuje tę decyzję i wykonuje część wrażliwą sprzętowo (publikacja, raster, PMG, timing).

Nie przenosić kodu krytycznego rasterowo/sprzętowo do C dla wygody i nie implementować nowego AI, lifecycle, polityki ruchu ani cadence ognia w ASM tylko dlatego, że renderer jest w ASM.

Pełna macierz własności: AGENTS.md („Architecture invariants / C / ASM ownership"). Granica, ABI i placement: docs/hybrid-c-architecture.md. Tego podziału nie powiela się w tym pliku.

5. Tryby pracy

Implementacja najpierw — dla odwracalnej pracy wysokiego poziomu w C (archetypy, AI, fale, reguły gameplayu): gałąź → implementacja → testy fokusowe → build XEX → krótki PAL smoke → owner smoke → commit lub rollback. Nie zastępować implementacji długim studium wykonalności.

Dowód najpierw — dla rastra, ANTIC, timingu PMG, VBI/DLI, backing/restore, placementu pamięci i innych zmian sprzętowych: pomiar lub proof przed integracją produkcyjną. Przed kosztowną przebudową przedstaw 2–3 tańsze warianty (efekt dla gracza, koszt, ograniczenia, ryzyko, rekomendacja).

Oddzielaj MEASURED od ESTIMATE. Nie ogłaszaj niemożliwości bez dowodu.

6. Tempo pracy

Tempo dostarczania funkcji jest równorzędnym ograniczeniem projektu. Długie kampanie PAL/raster rezerwujemy dla zmian w kernelu sprzętowym, zmian raster/PMG/ANTIC, kamieni milowych, bramek wydania i zaobserwowanych regresji czasowych. Nie powtarzaj pomiaru identycznego XEX; zmieniony XEX nie dziedziczy pomiaru poprzednika.

7. Owner smoke

Każda zmiana gameplayu lub renderingu wymaga owner smoke przed uznaniem jej za zaakceptowaną. Wersję przed smoke oznaczaj jako kandydata („OWNER-SMOKE CANDIDATE”), nie PASS. Przed przekazaniem XEX: build, bramki pamięci/transportu, zimny start. Nie przekazuj wersji z rozpoznanym crashem lub uszkodzeniem pamięci. Raport: co zmieniono, co potwierdzono, co niezweryfikowane, XEX i pełny SHA-256, komenda uruchomienia.

8. CPU i raster (PAL)

Target: 31 200 cykli. Hard gate: 32 568 cykli. Fizyczna ramka: 35 568 cykli. Nie myl tych granic.

Wall time jest warunkiem koniecznym, ale niewystarczającym: każdy writer pamięci widocznej przez ANTIC musi udowodnić poprawność względem rastra. Dynamiczny fence zależny od Y obiektu jest zabroniony. Znakowe nakładki fighter są publikowane w oknie po playfieldzie (wzorzec PairShot i Light).

Wynik scenariusza nie jest dowodem globalnego maksimum. Porównuj CPU tylko na identycznych scenariuszach replay.

9. Po BLOCKED / REJECTED

- zachowaj dowód w docs/diagnostics/;
- wycofaj własny odrzucony kod produkcyjny;
- nie uruchamiaj automatycznie kolejnych wariantów ani następnego punktu roadmapy;
- zaktualizuj STATUS (i plan, jeśli zmienia się kolejność), wskaż jeden następny krok.

10. Pojemność i stałe gameplayu

Minimum 4 przeciwników/zagrożeń jednocześnie, target 6, model 2 Heavy (P1/P2) + do 4 Light (bez własnego PMG). Architektura musi zachować mierzalną drogę do 2 Heavy + 2 Light i brak konstrukcyjnej blokady 2 Heavy + 4 Light. Fale: jeden dominujący archetyp + najwyżej jeden wspierający.

Bursty gracza 8/8/10 widocznych impulsów (4/4/5 PairShotów); 4/4/6 tylko diagnostycznie.

Nowy archetyp powinien wymagać danych, małego zachowania w C i ponownego użycia istniejącej klasy renderera ASM. Jeżeli wymaga przebudowy Directora, granica architektury wymaga przeglądu.

11. Pamięć i placement

[SUPERSEDED 2026-09-20 — decyzje właściciela A, B, C, Q oraz 22 i 23 §10.1; zapis w docs/owner-decisions-2026-09-11.md, sekcja „Decyzje literowe 2026-09-20". Wpisu nie usuwamy, bo jest historią tego, dlaczego tak było.]

BASIC RAM, zmiany loadera, runtime disk I/O i nowe mechanizmy transportu nie są domyślnym rozwiązaniem problemu placementu. Aktualizuj docs/memory-map.md przy każdej zmianie zarezerwowanego adresu. Ogólny zapas RAM nie zastępuje kontroli lokalnych granic segmentów, staging i transportu.

Co zmieniło grunt: ATR i tak wymagał wyłączenia BASIC-a (decyzja A), więc okno $A000-$BFFF jest bezwarunkowym RAM-em, nie obejściem (decyzja B); deadline bootu ATR został prze-bazowany na budżet 60 sekund (decyzja 22), więc runtime disk I/O nie kupuje się już czasem ładowania, którego nikt nie wybrał (decyzja 23 §10.1); a szesnaście poziomów ze zróżnicowaną grafiką capital nie mieści się rezydentnie (decyzje E i F), więc zmiana loadera jest wymaganiem treści, a nie skrótem zamiast inżynierii.

Co z tej reguły ZOSTAJE w mocy: „nowe mechanizmy transportu" nadal nie są domyślną odpowiedzią na placement — czytnik między poziomami ma uzasadnienie treściowe, nie placementowe. Zdanie o docs/memory-map.md i zdanie o lokalnych granicach segmentów obowiązują bez zmian; to one łapią realne błędy.

12. Kierunki odrzucone

Nie wracać bez nowych dowodów lub decyzji właściciela: pełny double buffer fighter playfieldu; globalny read-only visible ring; moving fence; stały sync $70 z szerokim oknem erase→redraw; pojedyncze okno publikacji jako samodzielne rozwiązanie konfliktów writerów; raster bands jako obejście ownership; per-access ownership lookup; dodatkowy background/ring 25 Hz; znakowi Raiderzy; osobny wrak Raidera przed przebudową debris; row-baked/blue far stars.

13. Kierunek capital traversal

Po zaakceptowaniu fighter foundation: okrągły ring wierszy jako coarse scroll + ANTIC VSCROL fine scroll. Nie przebudowywać przy tym scrollingu fighter.

14. Prompty wykonawcze

Każdy prompt implementacyjny wskazuje: model i effort, checkpoint, zakres, zakazy, kolejność weryfikacji, warunek przerwania oraz zasady commita/rollbacku. Odwołuj się do tego pliku zamiast przepisywać regulamin.

15. Aktualizacja reguł

Zmiana procesu aktualizuje ten plik i numer wersji. AGENTS.md i CLAUDE.md wskazują ten plik zamiast utrzymywać rozbieżne kopie.
